# Project state

2026-09-26: First test implementation on `build-v1.0` after the scaffold. Eight incremental commits added loader-shared config, perspective preservation, headset-relative camera positions with wall clipping, front-view rotation, and local-avatar rendering. Fabric and NeoForge both compile and reach the main menu with Vivecraft 26.2-1.3.15 under a virtual display. The Fabric mixin export confirms the two VR-transition camera-type invocations are intercepted; headset rendering and the full VR checklist remain unverified. An initial Fabric launch failed on mixin priority and an initial NeoForge launch failed because config read `Minecraft.getInstance()` before construction; both faults were corrected and each loader subsequently reached the menu. Do not describe this as a release or as hardware-tested.

2026-09-27: Replaced camera relocation and separate view-matrix rotation with render-pass-only `VRData.getEye` substitution. The render copy alone supplies per-eye third-person poses while `vivecraft$setupRVE` still sees the real eye; headset/controllers, sound listener and tick-time camera remain unmodified. One frame computes a head-center pivot, the vanilla 26.2 camera-distance expression (scale/vehicle), and 8-ray clipped zoom; first-person limb scaling, face overlays and nametag correction are disabled in third-person passes. `distance=0` now uses vanilla, and an existing `4.0` config remains an explicit override. Fabric and NeoForge Gradle builds passed; both revised clients reached the main menu under Xvfb without a mixin crash. Headset behavior, including front stereo and all hand/controller interactions, remains untested. This is a headset test candidate, not a release.

2026-09-27: Added character-anchored third-person tracking on top of the eye substitution. The lock ignores menu overlays; it cancels physical roomscale walking, pins world-space poses at tick start/end and pins the render copy to the interpolated player eye each frame. The shared head pivot drives both the anchor and camera. The start pin runs before Vivecraft captures pose history. Leaving the lock restores Vivecraft's normal room origin before building the next tick's poses when eligible, deferring the restore if Vivecraft's sneak counter would refuse it. Fabric and NeoForge builds passed after the exit-ordering adjustment. Each loader started under Xvfb with 3rdVive and Vivecraft loaded and reached resource/renderer initialization without a mixin crash; the bounded runs ended at their 110-second and 55-second timeouts respectively. VR poses and the full headset checklist remain unverified; a flat-screen launch cannot exercise the locked path.

The branch is pushed only when a testable build is ready for Elijah. `main` remains untouched; Elijah decides merging and releases.

2026-11-25: Ported `build-v1.0` to Minecraft 26.3 on branch `port-26.3` (version 0.2.0). Targets Fabric Loader 0.19.5+, Fabric API 0.161.0+26.3 (compile only), Vivecraft 26.3-1.3.18, NeoForge 26.3.0.118. Every mixin target was re-checked against Vivecraft's 26.3-1.3.18 source; all still exist with the same signatures, and Minecraft 26.3's per-pass extract/render split still runs inside `VRPassHelper.renderSingleView`, so the eye substitution scope is unchanged. Vanilla 26.3 `Camera` distance and `getMaxZoom` bytecode match `VanillaThirdPerson`. No Java source changes were needed. Fixes: the Vivecraft version range was hardcoded to 26.2 in `fabric.mod.json` and `neoforge.mods.toml` (would refuse to load on 26.3); it now comes from `vivecraft_min`/`vivecraft_max` in gradle.properties. README requirements and the stale "distance defaults to 4" note were corrected. Fabric build passed on Ubuntubox; a headless Fabric client reached resource loading with all 12 mixin target classes force-loaded and no mixin errors. The NeoForge jar was not built or launched on 26.3. Headset behavior remains untested.

2026-11-27: Branch `qol-ui-26.3` (version 0.3.0), from `port-26.3`. Menus, the VR keyboard (laser and physical) and the radial menu now open in front of the third-person camera instead of snapping to first person: while Vivecraft places or points at them, 3rdVive substitutes the camera for the head (`VRData.hmd` reads in `GuiHandler.onScreenChanged`, `KeyboardHandler.orientOverlay`, `RadialHandler.orientOverlay`) and camera-shifted controllers (`VRData.getController` inside the three `processGui` methods). Open menus slide with the camera each poll so head turns don't swing them out of view; screens shown over their block stay put. Grey menu hands are drawn at the shifted spot (`ArmsRenderState.extract`). With no screen, the HUD uses Vivecraft's head-lock path fed with the camera pose (`hudOnCamera`), without changing the Vivecraft setting. The pause-menu perspective button is removed; `key.togglePerspective` is added once to the radial menu (circle grown 8→10 when full). The perspective is saved in `thirdvive.json` on every `Options.setCameraType` and restored on the first tick, and is the same in and out of VR. Shared camera math moved to `ThirdViveCamera`. Config version 2 is saved by the game; older files get `firstPersonInMenus`/`debugLog` set false once. Fabric build passed on Ubuntubox; a headless Fabric client (Xvfb) force-loaded all 16 mixin target classes with no mixin errors, added the radial button and wrote config v2. NeoForge `createMinecraftArtifacts` fails on 26.3 (pre-existing, NeoForge setup step). Headset behavior is untested.

2026-11-27: 0.3.1 on `qol-ui-26.3`. Simplified per Elijah: character lock (`ThirdViveAnchor`) is now optional via `lockToCharacter`, default false, so roomscale walking works normally in third person unless enabled. Perspective persistence removed (`rememberPerspective`/`perspective` config gone); the perspective is vanilla's and 3rdVive only keeps Vivecraft from resetting it on VR on/off. Vanilla 26.3 does not save the perspective to options.txt, so it starts in first person after a restart. The radial menu is no longer grown: on first launch Toggle Perspective goes into an empty slot only if one exists; it is always selectable in Vivecraft's radial settings (its picker lists all non-hidden keybinds). Headset behavior is untested.

2026-11-27: 0.5.0 on `build-v1.0`. Simplified to "vanilla third person, in VR". Removed settings `distance` (always vanilla distance), `firstPersonInMenus` (never snaps to first person), `lockToCharacter` and `ThirdViveAnchor` (roomscale always works like normal Vivecraft) and `debugLog` with `ThirdViveDebug`/`SnapDetectorMixin`. Config versioning removed; old keys are ignored. `hudOnCamera` now covers the HUD, menus (chests, inventory), keyboard and radial menu: off places them where first person would. The snap-back guard (`RveRestoreGuardMixin`) now only acts in third person, so first person is untouched Vivecraft. Headset behavior is untested.

2026-11-27: 0.5.1. Brought back the character lock as `lockMovement`, on by default (`ThirdViveAnchor` restored; camera pivots on the head when locked, on the character eye when not). Reported but not yet fixed: in the back view the world looks smaller / wrong scale; front view is fine.

2026-11-27: 0.5.2. Fix: with lockMovement on, the player was dragged in one direction. Vivecraft roomscale walking moves the player to the feet position (feetBodyPosition with full-body tracking) or head pivot each tick, and the lock then moved the room after it, so it never settled. Roomscale walking (`VRPlayer.doPlayerMoveInRoom`) is now cancelled while the lock is on.
