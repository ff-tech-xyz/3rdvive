Goal
3rdVive lets a Vivecraft player use Minecraft's normal third-person camera inside the headset. Only the camera moves: all Vivecraft gameplay stays exactly as it is. The project layout is in the companion scaffold doc.
Required behavior
1. The toggle-perspective key works like vanilla in VR. F5 (or whatever it is rebound to) cycles first person → third person back → third person front, using vanilla's own CameraType.
2. The camera type carries across VR on/off. Switching into VR while in third person stays in third person, and vice versa. Vivecraft currently forces first person.
3. The camera is mounted 4 blocks away from the head, like vanilla. Back view sits behind the headset; front view sits in front and looks back at the player.
4. The camera orbits with the real head. It follows the headset's look direction, so turning your head swings the camera around you, and you always see yourself. Looking up physically makes the character look up, and the camera drops below the player, just like vanilla.
5. The camera doesn't clip through walls. It pulls in toward the head when blocked, like vanilla's zoom clipping.
6. Your full body is visible. Head, torso and legs render, and the model's arms and hands follow the controllers, holding items as Vivecraft already shows to other players.
7. Gameplay doesn't change. Aiming, block breaking, pointers, teleport, climbing, roomscale swings, menus, and the body pose sent to the server all keep using the real headset and controller poses.
Out of scope
• Any change to vanilla third-person behavior on flat screen.
• Any server-side component: the mod is client-only.
• Changing how Vivecraft animates the player model.
How Vivecraft blocks third person today
Vivecraft blocks third person in four places, all client-side. References are to the Multiloader-26.2 branch (1.3.15; the latest commit, 4320826, is from Sep 23, 2026). Paths are under common/src/main/java/org/vivecraft/.

Why this is good news
Vivecraft already builds a fully posed body (head, arms, body yaw) from the headset and controllers for the local player. It shows that body in the screenshot camera and the third-person mirror. Once the camera moves and these four checks flip, the player model is already correct. No animation code is needed.
The camera position and rotation are set per render pass: LEFT and RIGHT are the headset eyes, and CENTER is the desktop mirror. Moving the camera in vivecraft$setupVRCamera therefore moves both eyes and the flat-screen mirror together.

Use require = 0 on every @Dynamic or MixinSquared hook, so a Vivecraft rename disables that one feature and logs a warning instead of crashing.
1. The shared state helper
Every hook asks one question: "should this render pass use the third-person camera right now?"
public final class ThirdViveState {
    private static final Minecraft MC = Minecraft.getInstance();

    /** Third person is on and VR is running (ignores the render pass). */
    public static boolean active() {
        if (!VRState.VR_RUNNING || !ThirdViveConfig.enabled) return false;
        if (MC.options.getCameraType().isFirstPerson()) return false;
        if (MC.level == null || MethodHolder.isInMenuRoom()) return false;
        if (ThirdViveConfig.firstPersonInMenus
            && (MC.gui.screen() != null || KeyboardHandler.SHOWING)) return false;
        return true;
    }

    /** Only the headset eyes and the desktop first-person mirror get moved. */
    public static boolean activeForPass(RenderPass pass) {
        return active() && RenderPass.isFirstPerson(pass); // LEFT, RIGHT, CENTER
    }

    public static boolean isFrontView() {
        return MC.options.getCameraType().isMirrored(); // THIRD_PERSON_FRONT
    }
}
2. Keep the camera type across VR on/off
@Mixin(value = Minecraft.class, priority = 1500)
public class MinecraftMixin {
    @Dynamic("added by Vivecraft MinecraftVRMixin")
    @WrapWithCondition(method = "vivecraft$switchVRState",
        at = @At(value = "INVOKE",
            target = "Lnet/minecraft/client/Options;setCameraType(Lnet/minecraft/client/CameraType;)V"),
        require = 0)
    private boolean thirdvive$keepCameraType(Options options, CameraType type) {
        return !ThirdViveConfig.enabled; // skip Vivecraft's force-first-person and restore
    }
}
3. Give the toggle key back to vanilla
vivecraft$changeVrMirror is a Vivecraft mixin handler, so it needs MixinSquared. The handler checks VRState.VR_RUNNING; forcing that read to false makes it call vanilla's setCameraType.
@Mixin(value = Minecraft.class, priority = 1500)
public class MinecraftToggleKeyMixin {
    @TargetHandler(mixin = "org.vivecraft.mixin.client_vr.MinecraftVRMixin",
                   name = "vivecraft$changeVrMirror")
    @ModifyExpressionValue(method = "@MixinSquared:Handler",
        at = @At(value = "FIELD", target = "Lorg/vivecraft/client_vr/VRState;VR_RUNNING:Z"),
        require = 0)
    private boolean thirdvive$vanillaToggle(boolean vrRunning) {
        return vrRunning && !ThirdViveConfig.enabled;
    }
}
The side effect: the key no longer cycles Vivecraft's desktop mirror mode. The mirror stays settable in Vivecraft's menu. Optional: add a separate, unbound "Cycle VR mirror" key that calls vrSettings.setOptionValue(VRSettings.VrOptions.MIRROR_DISPLAY).
4. Move the camera
@Mixin(value = Camera.class, priority = 1500)
public abstract class CameraMixin {
    @Shadow private Entity entity;
    @Shadow private @Nullable Level level;
    @Shadow protected abstract void setPosition(Vec3 pos);
    @Shadow protected abstract void setRotation(float yRot, float xRot);

    @Dynamic("added by Vivecraft CameraVRMixin")
    @Inject(method = "vivecraft$setupVRCamera", at = @At("TAIL"), require = 0)
    private void thirdvive$offset(CallbackInfo ci) {
        RenderPass pass = ClientDataHolderVR.getInstance().currentPass;
        if (!ThirdViveState.activeForPass(pass) || this.level == null) return;
        ThirdPersonCameraMath.Pose p = ThirdPersonCameraMath.compute(this.level, this.entity, pass);
        this.setPosition(p.position());
        this.setRotation(p.yaw(), p.pitch()); // used for culling/particles, not the view matrix
    }

    @ModifyReturnValue(method = "isDetached", at = @At("RETURN"))
    private boolean thirdvive$detached(boolean detached) {
        return detached
            || ThirdViveState.activeForPass(ClientDataHolderVR.getInstance().currentPass);
    }
}
5. Turn the view for front view
The view matrix comes from getVRModelView, not from the camera's yaw and pitch, so front view has to be handled here too.
@Mixin(RenderHelper.class)
public class RenderHelperMixin {
    @ModifyReturnValue(method = "getVRModelView", at = @At("RETURN"))
    private static Matrix4f thirdvive$frontView(Matrix4f view,
                                                @Local(argsOnly = true) RenderPass pass) {
        if (ThirdViveState.activeForPass(pass) && ThirdViveState.isFrontView()) {
            // rotate 180° about the view's own up axis = turn the head around
            return new Matrix4f().rotationY((float) Math.PI).mul(view);
        }
        return view;
    }
}
6. Show the body, hide the floating hands
@Mixin(VREffectsHelper.class)
public class VREffectsHelperMixin {
    @ModifyReturnValue(method = "isFirstPersonEntityPass", at = @At("RETURN"))
    private static boolean thirdvive$showHead(boolean fp) {
        return fp && !ThirdViveState.activeForPass(ClientDataHolderVR.getInstance().currentPass);
    }
}

@Mixin(RenderPass.class)
public class RenderPassMixin {
    @ModifyReturnValue(method = "renderPlayer", at = @At("RETURN"))
    private static boolean thirdvive$renderSelf(boolean render,
                                                @Local(argsOnly = true) RenderPass pass) {
        return render || ThirdViveState.activeForPass(pass);
    }
}

@Mixin(VRArmHelper.class)
public class VRArmHelperMixin {
    @ModifyReturnValue(method = "shouldRenderHands", at = @At("RETURN"))
    private static boolean thirdvive$noFloatingHands(boolean hands) {
        return hands && !ThirdViveState.activeForPass(ClientDataHolderVR.getInstance().currentPass);
    }
}
With these flipped, VRPlayerModel stops hiding the head and arms, and the model's arms follow the controllers as Vivecraft already does for other players. Held items render in the model's hands through the normal third-person item layer.
Camera math
The camera sits on a line through the headset along its look direction, like vanilla does along the entity's look direction. Each eye keeps its own small offset from the head, so stereo depth still works.
View

View rotation
First person
Unchanged (Vivecraft)
Unchanged
Third person back
head − fwd · d + eyeOff
Same as the headset
Third person front
head + fwd · d + rot180(eyeOff)
Headset turned 180° about its own up axis
Definitions:
• head = vrData.hmd.getPosition() (world space)
• fwd = vrData.hmd.getDirection() (unit look vector)
• eyeOff = vrData.getEye(pass).getPosition() − head: half the IPD for LEFT/RIGHT, and about zero for CENTER
• d = min(config distance × world scale, clip distance). The distance defaults to 4.0, vanilla's value.
Front view must rotate eyeOff too. Otherwise the left eye renders from the right side and the depth inverts. Rotating a vector v by 180° about the headset's up axis u, where u = hmd.getCustomVector(0, 1, 0):
v' = 2\,(v \cdot u)\,u - v
This also reproduces vanilla's behavior when you look up. fwd points up, so the back-view camera lands below and behind the player, looking up at them.
ThirdPersonCameraMath.java
public final class ThirdPersonCameraMath {
    public record Pose(Vec3 position, float yaw, float pitch) {}

    public static Pose compute(Level level, Entity entity, RenderPass pass) {
        ClientDataHolderVR dh = ClientDataHolderVR.getInstance();
        VRData data = dh.vrPlayer.getVRDataWorld();
        boolean front = ThirdViveState.isFrontView();

        Vec3 head = data.hmd.getPosition();
        Vec3 fwd  = new Vec3(data.hmd.getDirection());
        Vec3 up   = new Vec3(data.hmd.getCustomVector(new Vector3f(0, 1, 0)));
        Vec3 eyeOff = data.getEye(pass).getPosition().subtract(head);
        if (front) {
            eyeOff = up.scale(2 * eyeOff.dot(up)).subtract(eyeOff); // rot180 about up
        }

        Vec3 dir = front ? fwd : fwd.scale(-1);
        double wanted = ThirdViveConfig.distance * dh.vrPlayer.worldScale;
        double d = clip(level, entity, head, dir, wanted);

        float yaw   = data.hmd.getYaw() + (front ? 180f : 0f);
        float pitch = front ? data.hmd.getPitch() : -data.hmd.getPitch(); // Vivecraft passes -pitch
        return new Pose(head.add(dir.scale(d)).add(eyeOff), yaw, pitch);
    }

    /** Same idea as vanilla Camera.getMaxZoom: 8 rays from a small box around the head. */
    private static double clip(Level level, Entity e, Vec3 from, Vec3 dir, double max) {
        double d = max;
        for (int i = 0; i < 8; i++) {
            Vec3 o = new Vec3((i & 1) * 2 - 1, (i >> 1 & 1) * 2 - 1, (i >> 2 & 1) * 2 - 1).scale(0.1);
            Vec3 a = from.add(o);
            HitResult hit = level.clip(new ClipContext(a, a.add(dir.scale(max)),
                ClipContext.Block.VISUAL, ClipContext.Fluid.NONE, e));
            if (hit.getType() != HitResult.Type.MISS) {
                d = Math.min(d, hit.getLocation().distanceTo(a));
            }
        }
        return d;
    }
}
The math is written from the Vivecraft source; it has not been compiled or run yet. Check two things in-game first: the pitch sign passed to setRotation, and the direction of the front-view matrix rotation. A wrong sign shows up immediately as an upside-down or mirrored view.
